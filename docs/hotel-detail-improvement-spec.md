# ホテル詳細「ホテルの詳細を見る」改善仕様書

## 1. 目的

検索結果カードの「ホテルの詳細を見る」を、ホテル紹介の補助画面ではなく「このホテルを遠征で選んでよいかを判断する画面」に作り替える。

今回調査した250会場×各3候補＝750件のホテル×会場関係データを利用し、特に会場アクセスを最上位の判断材料として表示する。

ホテル詳細ではホテル写真を表示しない。写真は検索結果カードに残してよいが、詳細画面は移動情報・宿泊条件・予約判断に表示領域を使う。

## 2. 現状の問題

現在の詳細ダイアログは左側にホテル画像相当の領域を持ち、右側に「向いている人」「会場までの移動」「料金目安」などを単純な縦並びで表示している。

会場への移動はホテル一覧の既存値を中心に表示しており、今回収集したホテル最寄駅、駅までの徒歩、駅間所要時間、乗換回数、会場最寄駅、会場までの徒歩、直通徒歩・バス・タクシーなどの詳細を使えていない。

また、調査精度が十分なレコードと一部情報だけ確認できたレコードを同じ方法で表示すると、未確認の合計時間を確定値のように見せる危険がある。

## 3. 使用データ

検索・ランキング・一覧表示の基本データは既存の `assets/data/hotels.json` を維持する。今回の変更で既存ファイルを750件の詳細データに置き換えない。

詳細専用として `assets/data/hotel-details.json` を追加する。生成元は研究ブランチ `research/hotel-details-750-20260807` の `research/generated/hotel_detail_research_750.jsonl` とする。

生成物は必ず750件、ID重複0件とする。研究用の `warnings`、検索失敗コード、内部用ステータス名は本番JSONへそのまま出さない。

## 4. 本番詳細データの構造

各ホテル×会場関係IDをキーにして、以下を保持する。

- `id`
- `hotelName`
- `venueName`
- `venueId`
- `venueNumber`
- `rank`
- `genre`
- `prefecture`
- `area`
- `coverage`: `complete` または `limited`
- `availability`: `active` または `closed`
- `access`
  - `heroMin`: 詳細上部に大きく出せる根拠付きの合計所要時間。完全確認レコードだけ許可
  - `mode`: walk / rail / bus / taxi / mixed / unknown
  - `directMin`
  - `hotelStation`
  - `hotelWalkMin`
  - `stationMin`
  - `transferCount`
  - `venueStation`
  - `venueWalkMin`
  - `routeSteps`: 画面用の順序付き経路
  - `note`: 非鉄道経路など利用者が知るべき補足
- `stay`
  - `priceEstimate`
  - `priceRange`
  - `plan`
  - `roomType`
  - `cancellation`
- `fit`
  - `role`
  - `summary`
- `bookingChecks`
- `checkedAt`
- `sources`

## 5. 情報精度の表示ルール

### 5.1 完全確認レコード

研究データが `verified` の場合のみ `coverage=complete` とする。

`direct_to_venue_min` が確認済みなら直通経路を優先し、それを上部の所要時間として使う。

直通経路がなく `total_access_min` が確認できている場合は、その値を上部の所要時間として使う。

### 5.2 一部確認レコード

研究データが `partial` の場合は `coverage=limited` とする。

この場合、区間ごとの確認済み値は表示してよいが、未確認区間を足し合わせて「会場まで約○分」とは表示しない。

上部は「確認できたアクセス情報」とし、「一部区間は合計せず、確認できた情報だけを表示しています」と案内する。

### 5.3 不明値

不明値を0、推定値、一般的な平均値で補完しない。

値がない項目は原則として項目自体を非表示にする。予約判断上必要な項目だけ「予約時に確認」と表示する。

### 5.4 営業終了情報

研究データに営業終了を示す内部警告があるレコードは `availability=closed` に変換する。

画面では内部警告コードを見せず、「営業終了情報があります。予約候補として使用しないでください」と明示する。

この場合、予約CTAは表示しない。

## 6. 詳細画面の情報優先順位

上から以下の順にする。

1. 会場名と候補順位
2. ホテル名
3. 会場までのアクセス要約
4. 実際の移動経路
5. 料金・プラン・部屋・キャンセル条件
6. このホテルが向いている人
7. 予約前の確認事項
8. 情報確認日と情報元
9. 比較・予約CTA

ホテル写真は入れない。

## 7. ヘッダー

既存ダイアログの閉じるボタンとアクセシビリティを維持する。

見出し直上に「○○会場｜候補1」のようなコンテキストを表示する。

主見出しはホテル名にする。

候補順位はランキングの根拠説明ではなく、同一会場内での候補位置を把握する目的で使う。

## 8. アクセス要約カード

画面の最重要領域とする。

完全確認レコードで合計時間がある場合は、左側に「○○会場まで」、中央または右側に大きく「約○分」を表示する。

併せて「徒歩」「電車」「バス」「タクシー」「複合」の経路種別を小さなラベルで表示する。

一部確認レコードでは大きな合計時間を出さず、「確認できたアクセス情報」と表示する。

## 9. 経路表示

経路は文章1行ではなく、順序付きのステップ表示にする。

鉄道利用例:

- ホテル
- 徒歩5分
- 新馬場駅
- 電車○分・乗換○回
- 天王洲アイル駅
- 徒歩1分
- 会場

同一駅の場合は「駅間0分」という不自然な表示を出さず、「同じ最寄り駅」と表示する。

直通徒歩の場合はホテル→徒歩○分→会場だけにする。

バスやタクシーが実用経路の場合は、鉄道経路へ無理に置き換えず、その交通手段をそのまま表示する。

## 10. 宿泊条件

PCでは2列までの情報グリッド、スマートフォンでは1列にする。

表示候補:

- 料金目安
- 想定価格帯
- 想定プラン
- 部屋タイプ
- キャンセル条件

価格は「料金目安」と明記し、最新料金であるような表現はしない。

キャンセル条件はプラン依存であることを前提にし、確定条件と誤認させない。

## 11. 向いている人

既存 `hotels.json` の `role` と `summary` を詳細データへ結合する。

アクセス情報の後に置き、ランキングカードのコピーをそのまま繰り返すだけではなく、遠征時の使い方を補足する。

## 12. 予約前チェック

既存ステータスで未確認のものがあれば、利用者向けの確認項目として表示する。

最低限「宿泊日当日の料金・空室」「プランごとのキャンセル条件」は予約サイトで最終確認する旨を表示する。

内部の検証コードや `partial`、`warning` などの開発用文字列は見せない。

## 13. 情報元

詳細下部に「情報の確認元」を置く。

ホテル公式、会場公式、経路確認元が存在するものだけリンク表示する。

URLそのものを長文で見せず、ラベルをリンクにする。

確認日は `checkedAt` を日本向けの日付表示に変換する。

## 14. CTA

詳細下部は予約判断の操作領域として固定する。

- 「比較候補に追加する」または「比較候補から外す」
- 楽天トラベル・じゃらん等の利用可能な予約リンク

予約リンクがない場合は空ボタンを作らない。

営業終了扱いのレコードでは予約リンクを出さない。

スマートフォンでは下端のsafe-areaを考慮したsticky領域にする。

## 15. PC表示

詳細ダイアログは現状と同程度の最大幅を維持するが、画像用の左右2カラムを廃止する。

本文を単一の読み順にし、アクセスカード→経路→宿泊条件の順で視線が自然に下がるようにする。

情報カードを細かく分割しすぎず、大きな3〜5ブロックにまとめる。

## 16. スマートフォン表示

詳細は既存どおり全画面ダイアログを利用する。

余白を16〜20px程度に抑える。

アクセスの大きな所要時間をファーストビューに入れる。

経路ステップは縦型にする。

CTAは本文をスクロールしても操作できるよう下部stickyにする。

## 17. フォールバック

`hotel-details.json` の取得に失敗しても、検索結果一覧そのものは壊さない。

詳細専用データを取得できない場合は、画像なしの簡易詳細を表示し、既存 `hotels.json` のホテル名、会場名、料金目安、役割、予約前確認を使う。

詳細データの失敗を理由にホテル一覧全体をエラーにしない。

## 18. 実装方法

既存 `app-core.js` を大幅に書き換えず、ホテル詳細専用モジュール `assets/js/hotel-detail.js` を追加する。

詳細ボタンのクリックをcaptureフェーズで受け、詳細専用モジュールが処理する。既存検索、比較、ランキング、ホテル画像ローダーには影響させない。

専用CSS `assets/css/hotel-detail.css` を追加する。

`assets/js/app.js` から専用CSSと専用JSを読み込む。`index.html` の `app.js` バージョンを更新し、ブラウザキャッシュで旧詳細画面が残るのを防ぐ。

## 19. データ生成

`scripts/build_hotel_details_production.py` を追加する。

GitHub Actionsで研究ブランチの750件JSONLを取得し、featureブランチ上の `assets/data/hotels.json` とID結合して本番JSONを生成する。

同時に検証結果 `research/generated/hotel_details_production_validation.json` を生成する。

## 20. 自動検証条件

以下を満たさない場合は生成処理を失敗させる。

- 研究レコードが750件
- IDが750件すべてユニーク
- `needs_review` が0件
- 本番出力が750件
- 本番出力IDが750件ユニーク
- 内部 `warnings` を本番JSONに含めない
- JavaScript構文チェックに合格
- 生成JSONが正常にJSONパースできる

## 21. 変更しないもの

- ホテルのおすすめ順位
- 会場ごとの候補数
- 検索条件UI
- 比較機能の基本仕様
- 検索結果カードのホテル写真
- 本番サイト全体のブランド配色

今回の対象は「ホテルの詳細を見る」と、その詳細を安全に支える750件のデータ統合に限定する。
